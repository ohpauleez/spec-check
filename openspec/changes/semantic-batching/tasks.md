### Unify Semantic Grouping change summary
- What changed: added a new shared grouping module `src/domain/formal/grouping.ts` containing `LogicalFileMappingError`, `activeMergedSpecsForGrouping()`, `buildLogicalFileByCapability()`, `selectClaimLogicalFile()`, `IndexedFormalizationClaim`, `SemanticClaimGroup`, `PhysicalClaimBatch`, and `groupFormalizationClaims()`. ### Clarify Failure Handling change summary
- What changed: added `src/domain/formal/degradation.ts` with `shouldDegradeBatchError(kind, claims)` — `timeout`/`invalid_json`/`schema_validation_error` degrade to per-claim inline retry; `prompt_too_large` degrades only when every per-claim inline prompt fits `PROMPT_ARG_MAX_BYTES` (measured in UTF-8 bytes); `spawn_error`/`invalid_files`/`invalid_timeout` become claim-level errors with no fallback; the `default` case is `assertNever(kind)`. It returns a boolean deliberately — no new public error taxonomy.
- Worker normalization: `formalizeClaims` wraps each physical batch's worker in try/catch so a worker-thrown failure becomes claim-level errors for only the affected batch via `workerFailureResult`; the outer `mapBounded` call is itself wrapped so a pool-level rejection still yields errors for all batches rather than dropping unstarted claims. The existing CLI abort behavior for zero candidates is unchanged (`PipelineAbortError("FormalizationError", …)` in `run-cli.ts`).
- Thrown adapter normalization: `sampleFormalizationsForClaim` catches `unknown` from `callOpencode` and converts it to a claim-level `FormalizationError`; `callAttachedAdapter` does the same for attached calls and reports a `transport_failure` outcome (see section 5 for the evidence-side redaction).
- Review counterexample: nested fallback initially ran with its own concurrency of 2, which let a degraded batch exceed the caller's configured concurrency bound. Fixed by making fallback sequential — `INLINE_FALLBACK_CONCURRENCY = 1` with the comment that each physical-batch worker owns one adapter slot. Verified by `test/contract/semantic-batching-concurrency.test.ts`, which observes that maximum in-flight adapter calls equal the configured bound across a 4-group run with attached failures plus inline fallbacks.
- Verification: `test/contract/semantic-batching-failures.test.ts` covers every handled `OpencodeError.kind` group — degradable kinds produce one inline call per claim and record `model_failure`; infrastructure kinds produce claim errors with no fallback and record `infrastructure_failure`; `prompt_too_large` has both branches (fits → fallback; one oversized claim → immediate claim errors, no fallback calls); a thrown single-claim adapter failure is normalized with the claim ID attached; and a `mapBounded` mock that throws for indexed worker items proves sibling-batch isolation (`expectClaimPartition(result, [2, 3], [0, 1])`). Temp lifecycle fault cases are covered in `test/contract/batch-evidence.test.ts`.

### Identity And Ordering change summary
- What changed: the original eligible index is now the authoritative internal identity. `groupFormalizationClaims` assigns `eligibleIndex` in eligible-claim order; it flows through `IndexedFormalizationClaim`, into `BatchContextFile.claims[].index`, and into `matchAttachedBatchResponse` which validates each returned `index` against the attached set (unknown, duplicate, missing, non-integer, or count-mismatched indexes reject the whole mapping as `schema_validation_error` while per-entry Logic IR failures stay per-claim). `FormalizationCandidate` gained `eligibleIndex?: number` (optional only for compatibility with hand-built candidates) and `FormalizationError` gained `eligibleIndex?` plus `claimId?`; `pipeline-types.ts` mirrors the error shape.
- Additional-sample merging reworked: `addAdditionalSamples` now builds a `Map<number, FormalizationCandidate>` keyed by eligible index and merges via `byIndex.set(...)`; candidates missing an index produce an error result rather than an ID-keyed merge. Final `candidates` and `errors` are sorted by eligible index via `compareCandidates`/`compareErrors` (missing index sorts last).
- Bug fix (pre-existing): the old implementation merged additional samples by `claim.id`, which could cross-merge samples between distinct claims when IDs were absent or duplicated. The change's design.md explicitly identifies this as the bug being fixed; the index-keyed merge removes it structurally.
- Property-test counterexample: the grouping-parity property test initially used the shared fallback display ID `"UNNAMED"` for claims without IDs, which collapsed distinct missing-ID claims in the comparison. Fixed test-side by using per-file fallback IDs (`UNNAMED-${provenance.file}`) while the implementation keys strictly on eligible index; a dedicated property test generates even-index claims sharing `id: "DUPLICATE"` and odd-index claims with no ID and asserts indexes still partition exactly.
- New findings: `formalization.sample_shortfall` (bounded retry budget preserved a valid candidate but not the requested sample count; evidence carries `valid_samples`/`requested_samples`) and `formalization.additional_sample_failed` (first valid sample preserved; evidence includes `eligible_index`).
- Verification: SAFE-18 (`test/invariant/safety-liveness.invariant.test.ts`) runs `samplesPerClaim: 2` over duplicate and missing IDs and asserts per-candidate sample counts of 2 with four inline additional-sample calls; the concurrency contract test proves candidates/errors stay in eligible order even when sibling groups complete out of order.

### Evidence Preservation change summary
- What changed: `batch-transport.ts` defines `BatchAttemptEvidence` (schema version, `batchKey`, `claimIndexes`, `claimIds: (string | null)[]`, `provenanceFiles`, `contextSha256`, `promptVariant`, `model`, `subBatchOrdinal`, `outcome: BatchAttemptOutcome`, `cleanup: BatchCleanupOutcome`) plus the pure constructor `buildBatchAttemptEvidence`. - Lifecycle discipline: `runAttachedTransport` constructs an `evidenceDraft` (placeholder outcome, `cleanup: "not_attempted"`) *before* the `try/finally` that runs the adapter and cleanup, and `formalizeAttachedBatch` finalizes the record after cleanup as `{...transport.evidenceDraft, outcome: assembled.outcome, cleanup: transport.cleanup}`.
